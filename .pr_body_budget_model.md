## Screenshots / Proof of Fix

Runbook against a live proxy hitting a real provider. Start the proxy with `python litellm/proxy/proxy_cli.py --config litellm/proxy/dev_config.yaml --detailed_debug --reload --use_v2_migration_resolver 2>&1 | tee litellm.log`, create a key with a tiny budget, spend it, then make one more call:

```
# create a key with a $0.0001 budget
curl -s http://localhost:4000/key/generate -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" -d '{"max_budget": 0.0001, "models": ["gpt-4o-mini"]}'

# burn through the budget with a couple of real calls, then the next call:
curl -s http://localhost:4000/v1/chat/completions -H "Authorization: Bearer <generated_key>" \
  -H "Content-Type: application/json" \
  -d '{"model": "gpt-4o-mini", "messages": [{"role": "user", "content": "hi"}]}'
```

Expected 429 response now names the model:

```
{"error":{"message":"... Current cost: ..., Max budget: 0.0001 Requested model: gpt-4o-mini","type":"budget_exceeded","param":null,"code":"429"}}
```

The same enriched message appears in `litellm.log` and in the Logs UI: open http://localhost:4000/ui/?page=logs, open the failed row. The Model column shows `gpt-4o-mini` and the error detail reads `... Requested model: gpt-4o-mini`.

## Changes

Budget checks run during auth, before the request is routed, so most `BudgetExceededError` messages (key, team, team-member, user, end-user, organization, project, tag, and the global proxy budget) never named the model the caller asked for; only the per-model budget limiter included it. That left customers unable to tell which model a rejected call was for, both in the API response and in the Logs UI error detail.

This appends the requested model in the single auth exception chokepoint, `UserAPIKeyAuthExceptionHandler._handle_authentication_error`, rather than touching every raise site. The append happens at the top of the handler's error branch, before the failure hook logs the error and before it is converted to a `ProxyException`, so the model reaches the client response, the proxy logs, and the Logs UI error_information, which records `str(exception)`. Re-syncing `e.args` keeps `str(e)` in step with `e.message`. The model is resolved with `get_model_from_request`, the same resolver the budget checks themselves use, so the named model matches the one that was evaluated and also covers routes that carry the model in the path or query (for example Azure deployment routes) rather than the request body. A guard skips messages that already contain `model=<name>` so the per-model limiter messages are not double-printed.

The Logs UI Model column is populated separately from the error message, by the failed-request spend logger from `request_data["model"]`. For failures rejected before routing, or routes that carry the model in the path, that field can be empty and the column shows blank. The failed-request hook (`_ProxyDBLogger.async_post_call_failure_hook`) now backfills the model from the route with the same resolver when the body has none, so the column is filled too.

Tests cover the message helper directly (model in the body appended to both `message` and `str()`, model resolved from a path-param route with an empty body, no double-print when the model is already present, non-budget exceptions untouched, and no model anywhere leaving the message unchanged), an end-to-end pass through `user_api_key_auth` proving the model from the request body reaches the final `ProxyException`, and the spend-log backfill (model resolved from an Azure deployment-style route when the body has none, and a body model kept verbatim over the route). Reverting either change makes the corresponding tests fail.
